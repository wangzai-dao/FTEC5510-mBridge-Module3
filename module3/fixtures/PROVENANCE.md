# Fixture provenance

Everything under `fixed_demo/` and `pilot/` is **copied verbatim** from the
Module 2 repository; nothing was modified. Both bundles exist so that the CI
pipeline is self-contained: a fresh clone can run the full acceptance suite
without access to the (private) Module 2 repository.

## `fixed_demo/` — hand-checkable contract fixture

| Item | Value |
|---|---|
| Source repository | `FTEC5510-mBridge-Module2-Copy` (private) |
| Path inside that repo | `examples/fixed_demo/` |
| Files | `config.json`, `payments.csv`, `inflows.csv`, `expected_exogenous_events.csv`, `manifest.json` |
| `dataset_id` | `fixed_demo_v1` |
| `schema_version` | `1.0.0` |
| Scale | 10 payments, 3 inflows, 7200-second observation window |

This one is small enough to verify by hand, and it separates *notice* from
*cash*: `I000001` is announced at 210 s and credited at 450 s. Module 3's
acceptance tests check the engine reproduces exactly that timeline.

## `pilot/` — the seven-scenario pilot set

| Item | Value |
|---|---|
| Source repository | same |
| Path inside that repo | `outputs/pilot/<scenario>/seed_<n>/` |
| Files kept | `config.json`, `payments.csv`, `inflows.csv`, `manifest.json` |
| Datasets | 21 = 7 scenarios x 3 pilot seeds (1001, 1002, 1003) |
| Total size | about 200 KB |

`expected_exogenous_events.csv` is omitted here: only the fixed fixture needs it,
and the engine never reads it. It can be regenerated by Module 2 at any time.

The seven scenarios are `baseline`, `low_rmb_liquidity`, `payment_surge`,
`large_payments`, `tight_deadlines`, `delayed_inflows` and `fx_capacity_shock`.
Every one of them is executed in CI, for all five strategies, so liquidity
constraints, arrival surges and FX shortages are all exercised on every push.

## `formal/` - the 30-seed reporting set

| Item | Value |
|---|---|
| Source repository | same |
| Path inside that repo | `outputs/formal/<scenario>/seed_<n>/` |
| Files kept | `config.json`, `payments.csv`, `inflows.csv`, `manifest.json` |
| Datasets | 210 = 7 scenarios x 30 formal seeds (20001-20030) |
| Total size | about 2 MB |

These are the seeds behind every number reported in the final report; the pilot
seeds must never be used for that, or the parameters would be tuned on the same
data they are evaluated on.

CI does **not** execute the formal set on every push - that would add roughly
35 s per job for no correctness benefit. Run it explicitly when producing results:

```bash
python module3/scenario_report.py --root module3/fixtures/formal
```

The formal bundle is the only bulky part of this directory. If repository size
ever becomes a problem, it is the first thing to move to an external archive;
`upload_to_github.py` skips unchanged files, so re-adding it later is cheap.

## Why bundle data at all

`fixtures/` duplicates data that Module 2 owns. That is a deliberate trade-off:

1. CI cannot reach the private Module 2 repository without embedding a token,
   which is not acceptable in a course project;
2. the bundled copy is pinned, so a failing test always has the exact input that
   produced it;
3. the fixture version travels with the code, so the two cannot drift apart
   silently.

## Integrity constraint

Each dataset's `manifest.json` records the SHA256 of its own input files.
`m3engine.io.load_dataset()` verifies them by default and fails immediately if any
file has been altered.

**Do not edit anything in this directory by hand.** To refresh a bundle, copy it
again from Module 2 and confirm that

```bash
python -m unittest discover -s module3/tests -v
python module3/scenario_report.py --root module3/fixtures/pilot
```

still succeed.

## This is input, not results

These files contain exogenous events only — payment arrivals, inflow notices and
inflow credits. They contain **no settlement outcome**. Settlement results are
produced at runtime:

```bash
python module3/run_engine.py --dataset module3/fixtures/fixed_demo --strategy all --out module3_outputs
```
